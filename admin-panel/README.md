# Voiza Admin Panel

Back-office for the Voiza audio party platform: live stats, user moderation, room
monitor, virtual gift store and the R-coin withdrawal queue.

Stack: **Vite + React 18 + TypeScript + Tailwind CSS 3** (classic `tailwindcss@3` +
`postcss` + `autoprefixer` pipeline). No UI kit, no chart library — everything is
built from the small component set under `src/components/ui/`.

## Run standalone (development)

```bash
cd admin-panel
npm install
cp .env.example .env.local   # optional: point at a non-default backend
npm run dev                  # http://localhost:5173
```

`vite.config.ts` proxies `/api` to `http://localhost:4000` during development, and
`src/lib/api.ts` also calls `VITE_API_BASE_URL` directly when it is set.

Production build: `npm run build` (emits `dist/`), preview with `npm run preview`.

## Run via Docker Compose (full stack)

From the repository root:

```bash
docker compose up --build
# admin panel -> http://localhost:5173  (container serves nginx on port 80)
# backend     -> http://localhost:4000
```

The containerized panel serves the SPA with an nginx fallback and reverse-proxies
`/api` to the `backend:4000` service (see `nginx.conf`), so no CORS setup is
needed *when the bundle is built with a same-origin base*. That is the catch:
`apiBase()` defaults to `http://localhost:4000` and dials the backend directly, so the
proxy is only on the path if `VITE_API_BASE_URL` is set to the panel's own origin (an
empty string works and is what makes it same-origin). To build against a different API
base baked into the bundle:

```bash
docker build --build-arg VITE_API_BASE_URL=https://api.example.com -t voiza-admin .
```

`nginx.conf` listens on 443 and redirects 80, so it expects a certificate at
`/etc/nginx/tls/fullchain.pem` with its key at `/etc/nginx/tls/privkey.pem` and **fails to
start without them** — that is the intent for a public deploy, not a local one. To run the
container over plain HTTP, delete the 443 server and the redirect. Two things it also
carries that are easy to lose when the file is rewritten: `/socket.io/` is proxied with
`Upgrade`/`Connection` headers and a 120s read timeout — the ops console dials that path
websocket-only, so without the block a same-origin build gets an HTML body where the
handshake should be and the room monitor never goes live — and HSTS is emitted only when
the request actually arrived over TLS, so a local http:// panel cannot get itself pinned.

## Signing in

The panel authenticates against `POST /api/admin/login` (username + password, JWT
bearer afterwards). On a fresh stack the backend seeds a super-admin from
`ADMIN_USERNAME` / `ADMIN_PASSWORD` — with the defaults shipped in the root
`.env.example` that means username **`admin`**, password **`voiza-admin`**. Rotate
them (and `JWT_SECRET`) before exposing the panel. The alternative bootstrap path is
`POST /api/auth/verify-otp` with `ADMIN_BOOTSTRAP_PHONE` + `ADMIN_BOOTSTRAP_OTP`,
which returns an admin-scoped token for the same operator.

The sign-in screen prints those defaults as a bootstrap hint, but only under
`import.meta.env.DEV`. That is inlined at build time, so the block is dead-code
eliminated from a production bundle rather than merely hidden at render — verify with
`grep -r voiza-admin dist/assets/` after `npm run build`, which must return nothing.
`/api/admin/login` itself is throttled at 10 attempts per minute per IP and username;
a locked-out operator gets `429` and the message is shown as typed.

Two answers end the session rather than showing an error. `401` means the twelve-hour token
expired. `403 operator_disabled` means someone switched this account off on **Operators** since it
signed in, and it is treated the same way even though the status code differs: the guard re-reads the
row on every request, so a token cannot outlast the switch, and every screen this operator opens from
now on would answer identically. A different `403` — `permission_denied` — does not log anyone out;
that is a role that does not reach this route, and the operator is still signed in.

## Feature map

| Route           | What it does                                                                     |
| --------------- | -------------------------------------------------------------------------------- |
| `/`             | Overview: KPI cards, 7-day diamonds/rooms SVG trend chart, live rooms shortlist   |
| `/users`        | Search/filter/paginate users, adjust diamond/R-coin balances, ban/unban. **Bonus diamonds** (`promo_grants`, migrations `0036`/`0037`) appear in two places on this screen. A member holding any prints a violet `+420 bonus` line under their diamond count and is never summed into it: one pocket is bought and permanent, the other is minted and expiring, and an operator reading "1,300" cannot tell which half the member can still send a room with. The **Bonus** button opens the per-account dialog — Bought / Bonus / Next to expire as three separate figures, then the grant ledger (minted, amount, left, status, reason, expiry) with a switch to include spent and lapsed rows, because "where did my bonus go?" is answered by a `LAPSED` line. "Next to expire" counts down to the earliest live deadline, which is a fuse that has not burned yet and so cannot be answered by `relativeTime`, whose entire vocabulary is past tense. Minting takes an amount (≤10M), a reason of at least three characters (it is the audit trail, not a comment) and an optional day count that falls back to the policy's expiry; reading needs `user:read`, minting `user:wallet`. Every accepted click is its own grant: an operator mint carries no de-duplication key, since "the same giveaway twice" and "the same campaign twice" are indistinguishable here, so the only guard against the accidental double is the button staying disabled until the server answers — and what the server then pushes over `wallet:update` is the wallet's total, not this grant's remainder, or the phone would quote one batch as the whole pocket. Above the table, the **Promotional diamond policy** card edits `accounts.promotional`: default expiry in days and which sinks the pocket may feed (gift / box / store / game), saved by `PUT`, which replaces the whole blob, so the save spreads the stored object and overwrites only the two keys it edits — a key another tool added survives. Reading that card needs `finance:read`, writing it `config:manage`, sweeping `user:wallet`. Closing a sink is not cosmetic: the ledger then quotes `promotional: 0` in the affordability split it sends back, and a member whose purchased pocket cannot cover the price is refused with `insufficient_balance` while still seeing bonus coins on their own screen — which is why the panel can promise the dial is what phones obey. "Expire due grants now" POSTs `promo-grants/lapse` and reports what actually died rather than what was asked — on a window whose grants are not yet due that is "Nothing was due to expire," and a real run prints the count and the diamonds released, each reversing its own `PROMO_GRANT` entry with a `PROMO_LAPSE`. The backend sweeps on its own every 60 seconds, so the button is a convenience and not the only thing that closes a dead grant |
| `/rooms`        | Room monitor: seat policy card (default speaker seats and the largest room a host may pick, `config:manage` to write, `room:read` to view), 5s polling, force-close, seat/audience drawer with disconnect |
| `/rooms/:id`    | Ops console: live seats/chat/listeners over Socket.IO, mute/lock/disconnect/ban, moderator announcement, host warning and the theme picker (`lottie-web` previews the generated animations) |
| `/gifts`        | Virtual store CRUD with live validation, inline active toggle, a ticker/full-screen effect tier selector, a Lottie preview of the gift overlay and an Upload button on each art field (`media:manage`; the URL box still accepts a CDN path by hand). **Lucky gift boxes** (`gift_box_outcomes`, migration `0027`) are edited in the same form: an `isLuckyBox` switch, one dial — `receiverShareBps`, typed as a human percent, with the platform's residual printed beside it ("Receiver keeps 60%" → the box banks 40%) — and a prize table you add to, remove from and edit in place (label, a `×2.5` multiplier that maps to 25000 bps, a relative weight), capped at 20 rows because a longer table cannot disclose its own odds. Each row live-prints the odds it produces in both units (`1 in 40 · 250 bps`), and a running line below the table states the expected multiplier and what the box pays of its own pool on average. That line is the server's guard, mirrored: `floor(Σ(multiplier × weight) / Σ weight)`, then `floor(expected × share / 10000)`, the same floors in the same order, so an operator sees "on average this box pays 250% of what it sells for" while typing rather than after a 400. The warning is deliberately non-blocking (the ladder is half-typed a lot) and the write still refuses. Updates go by `PUT` — `PATCH` 404s on this path — and the prize table is re-sent only when the table itself changed, since an omitted `boxOutcomes` means "leave the stored draw alone" while `boxOutcomes: []` on a live box is a refusal; switching a box off sends the flag alone, which is what deletes its prizes. Box rows carry a `box` badge in the grid with every prize and its odds printed under the price, so the draw is readable without opening the editor, and the earnings table flags box rows and prints **Paid / spent** (R-coins against diamonds), which on a box is the realised payout rate of the rolls rather than the price list's margin. Refusals arrive as stable `error.code` values and are rendered as sentences, not statuses: `lucky_box_needs_outcomes`, `lucky_box_too_many_outcomes`, `lucky_box_needs_reward_pool`, `lucky_box_outcomes_without_box`, `lucky_box_outcomes_invalid` and `lucky_box_payout_unbounded`, whose `error.details` (`expectedMultiplierBps`, `receiverShareBps`, `payoutRatioBps`) are worked into that sentence. A field the server rejects by bounds (`requireInt`/`requireString`) answers with `bad_request` and names the row, e.g. `boxOutcomes[0].weight must be >= 1`, which the panel shows as the server wrote it. The arithmetic and the phrasing live in `src/lib/lucky-box.ts`, mirroring `backend/src/services/lucky-box.service.ts` |
| `/withdrawals`  | R-coin cash-out queue, in the three steps the money actually takes (migration `0032`): **PENDING → APPROVED → PAID**, with **REJECTED** reachable from either open step. The status filter defaults to Pending, and the action column changes verb with the row — *Review* on PENDING, a green *Pay* on APPROVED, nothing on a closed row, because a screen that offers "approve" on an approved request teaches the operator that the button means nothing. The amount cell prints the split under the gross (`−1.2k fee · 48.8k paid`) so the fee is readable without opening the dialog, and a PAID row shows its `payoutReference` under the badge — the number a host calls about a week later. Review takes a decision plus an optional note and says what accepting promises: "the host is owed R 48.8k", not "approve". Pay refuses to open its button until the reference has three characters, since the release is the one step the book cannot verify on its own. A card under the table edits the **cash-out policy** — `accounts.withdrawal`, `{minRCoins, feeBps}` — with a worked example recomputed as you type ("A R 100k cash-out would pay the host R 95k and keep R 5k"), because a bps number nobody can mentally divide is a dial that gets set wrong. Writing it needs `config:manage`; the queue needs `withdrawal:review`, which covers accepting, refusing and paying — the same split the server enforces, and `admin_audit` still records `WITHDRAWAL_REVIEW` and `WITHDRAWAL_PAY` as separate verbs so who accepted and who released the money stay distinguishable |
| `/media`        | Media library: upload gift icons, Lottie gift scenes, gift sounds, room wallpapers, room effects, entrance rides and rank badges (base64 over `POST /api/admin/uploads`), then list, preview, copy the stored path or delete a file. Needs `media:manage`; a file a catalogue row still points at cannot be deleted |
| `/banners`      | Promotional art (`banners`, migration `0028`) for the four surfaces a phone draws it on — splash, home, gift panel, game desk — in one list with a tab per placement. The card header prints what `GET /api/banners` publishes right now per placement, so a saved row is provably on the wall rather than only in the database, and each row shows its own status derived the same way the server derives it (`Switched off` / `Starts …` / `Ended …` / `Room has closed` / `On the wall`) with impressions, taps and the click-through rate beside it. `ArtField kind="BANNER"` uploads the seven containers the media slot accepts; the format select has to match the file, since that string is what chooses the renderer on the device, and the preview under it renders Lottie (`lottie-web`), plays MP4 and names SVGA as app-only. The tap target is a verb plus a value — nothing, one of the four internal screens, a room picked from `api.listRooms({status:'ACTIVE'})` (a retired room still shows as an option so an old campaign is editable, and the row is then flagged red because the read path hides it), or an external `https://` link — and switching the verb clears the value rather than carrying a room id into a link box. Retiring is the inline switch, which writes `isActive` and then re-reads the public list to prove the banner actually left the phone; the delete dialog prints the counts the delete destroys and says so in those terms. `key` is immutable. Reading needs `dashboard:read`, writing `config:manage`, uploading `media:manage` |
| `/emoji`        | Chat emoji catalogue the room picker reads: search by key, name or code, then create/edit/delete a row (key, label, art URL or Upload, order). The card header prints how many codes `GET /api/emoji` currently publishes and the `codePattern` clients scan messages with, so a saved row is provably live on a phone. `key` is immutable after creation — sent messages are spelled after it — and deleting one leaves those messages as text instead of rewriting them. Reading needs `room:read`, writing `config:manage`, uploading `media:manage` |
| `/ranks`        | The earned level ladder (`rank_levels`, migration `0017`): every rung with its floor in XP, name, accent colour, badge art and how many members sit on it. A card at the top prints the two rates the server actually awards at — 1 XP per diamond spent, 0.5 per R-coin earned — and the row list compares each rung against `GET /api/ranks`, so a saved rung is provably published to phones rather than only written to the database. `level` cannot be edited (it is the key accounts sit on): renumbering means adding the new rung and deleting the old. Client-side checks mirror the server's — floors must strictly increase, level 0 must cost 0, `#rrggbb` only, art must be `/…` or `https://…` — and the badge preview loads from the same URL a phone uses, so missing art breaks here first. Deleting a rung moves its members down by XP, and level 0 refuses. Reading needs `user:read`, writing `config:manage`, uploading `media:manage`. Experience itself is corrected per account from **Users → Level**, which posts a signed delta with a reason and records `USER_XP_ADJUST` in the audit log |
| `/decor`        | Room decoration CRUD — the themes a host can pick and the Lottie loops a room plays. Themes: name, slug, accent colour, wallpaper (Upload or a CDN path by hand), default switch, room count, live preview. Effects: `AMBIENT`/`WELCOME` tabs, key, name, URL, order, and a "published" badge that compares the row against `GET /api/rooms/themes` so an operator sees the catalogue a phone will actually read. Plus one dropdown per room category choosing its ambient loop. Reading needs `room:read`, writing `config:manage`, uploading `media:manage`. A theme in use by rooms can be retired (those rooms fall back to the default art); an effect still mapped to a category is refused with `effect_in_use`. **Entrance rides** (`profile_rides`, migration `0026`) are the fourth sellable catalogue on this screen: the full-screen cinematic a room plays while a member joins, listed with the same price/VIP/recommended badges as a frame plus its renderer and its screen budget — a `durationMs` of `0` reads as "asset length", never "0 ms". The form takes key (immutable, so an update never sends it), name, file (Upload as the `RIDE` media kind or a CDN path by hand), renderer (`LOTTIE`/`SVGA`/`MP4`), budget in ms with the 0 / 250–30000 rule spelled out inline, order, price, on-sale switch, period (blank = permanent), VIP level and recommended. Client checks mirror the server's refusals (`ride_fields_missing`, `ride_exists`, `ride_format_invalid`, `ride_duration_invalid`, `ride_price_required`, `ride_price_without_sale`) and the server's own sentence is still shown when it says no. Each card has a "who holds this" list and a delete confirmation that reports how many members keep their receipt and stop playing it |
| `/finance`      | The double-entry book (`fin_journal_entries` / `fin_journal_lines`, `fin_accounts`), in four tabs. **Automated tie-outs** each print a count of the rows that violate their own rule, so a breach is queryable rather than arguable, and a pass says only that these tie-outs hold for this window. **Trial balance** sums every debit and credit line per account and flags the pair if they differ. **Chart of accounts** and **Journal** are paged reads of the same book; the Journal filter lists
`GIFT_TAX`, `GAME_TAKE`, `WITHDRAWAL_FEE`, `AGENCY_COMMISSION` and `AGENCY_SETTLEMENT` beside the money
kinds — the first two are the coin spreads each gift and each settled game keeps (migration `0031`), the
third is the fee a paid cash-out kept (`0032`), and the last two are the same agency money written twice:
the accrual that owed it when a host's gift landed, and the entry that moved it when the transfer was
recorded (`0033`). All of them are posted in `pkr` at `system_config.accounts.coinValue`
rather than as coin counts, so they tie out against the revenue account like any other entry. Real money is always minor units and every figure is printed with its currency code; `Export report` downloads the tie-outs as CSV. Needs `finance:read` |
| `/applications` | Become a Partner, from the deciding side (`role_applications`, migration `0035`) — the only screen in this panel whose buttons mint a privileged role, so it is built around the two things a grant can get wrong. **A role is this row**, not a column on the member: approving writes the decision and activates the agency or partner account beside it, and the row afterwards reads back as the proof; a `user_type` badge on the member's own profile is displayed here and trusted by nothing. **The applicant is never chosen here**: every row on this queue was filed by the account whose name and phone are printed beside it, there is no user field to fill in, and the form the member answered was the form the backend published, so the answers are rendered with the server's own question labels from `GET /api/admin/partner-applications/forms` — a question added on the backend appears here with the same words the member saw, and a `preferredAgencyId` prints an agency name rather than a uuid. Filters: status (defaults to Pending, because that is the queue), role, and a search that matches a username or the phone behind it. One dialog holds three decisions — Approve, Request more information, Reject — and a fourth verb, **Revoke**, that only appears on an `APPROVED` row: a granted role is not re-decided, it is taken back, and taking it back suspends the agency or the partner account the approval opened rather than merely flipping the status. Approve is the only one that can be filed without a sentence; the other two need at least three characters, because the server refuses them with a 400 otherwise and a member has to be able to read *why* — the same text is what their app then prints under the decision. Approving a coin seller also picks the BD account it reports to from the active BD roster, and the button stays dead until one is chosen, because `seller_bd_required` is a refusal this screen can predict; the other refusals are shown as the server's own sentences — `agency_name_taken`, `invalid_parent`, `multi_manager_disabled`. Each row prints who last touched it by username and when, and the full life of the application is on `/audit` under its own verbs. A card under the table edits `roles.hostApplicationRequired`, which is not a filter on this page but a platform-wide switch: with it on, every account holding no approved partner role is refused a room, which is why it ships off and why the dialog says so. Reading needs `application:read` and every decision needs `application:review`, so a `FINANCE_ADMIN` gets the queue with the actions replaced by a line naming the permission that is missing — and the server refuses the write anyway |
| `/accounts`     | Purpose accounts (`fin_accounts` projected by `purpose_account_balances`, migration `0029`) — every balance the platform owes or holds, read from the table that owns it and labelled as such in the "Read from" column (`users.diamond_balance`, `users.r_coin_balance`, `fin_journal_lines`). **The book**: search, category / owner-kind / status / currency filters, an "only with a position" switch and pagination; balances, holds and statement amounts are all rendered through `formatUnitAmount`, so `dmn` and `rcn` print as whole coins and `pkr` as minor units — a number without its unit is a number a partner disputes. Opening a row gives the six projection cells, a lifetime sentence (in − out + opening against the balance it claims), the paged statement with a date window and CSV/Excel export, the holds on that account with a **Release** button, and the two writes: place a hold (kind, amount in that account's own unit, reason ≥ 8 chars) and change status. Both send an idempotency key generated per click, so a retry after a lost response replays instead of freezing the same money twice, and after either write the drawer re-reads the account rather than reusing what it had displayed. A hold is carved out of `available` rather than off it, so the drawer prints `available − frozen` as what a new hold could still take — the same figure the server uses when it answers `freeze_exceeds_available`. **Reconciliation** lists the tie-out findings with their severity, account and amount; **Open holds** spans the whole book and links each hold to the account behind it. This screen never edits a balance — that route stays on `/users`. Reading needs `account:read`, both writes need `account:manage`; an `OPERATIONS_ADMIN` token gets the same book with the actions replaced by a note saying which permission is missing, and the server refuses the write anyway (`403 permission_denied`). Exported workbooks are validated by `backend/scripts/account-e2e.cjs`, which inflates every entry and recomputes its CRC |
| `/operators`    | The roster behind this panel (`admins`, migration `0030`) — who may sign in, and what happens when they must not. **There is no delete button and there never will be**: an operator who has written one audit row cannot be removed at all (the database refuses it, `backend/scripts/operator-e2e.cjs` pins it), so the lifecycle offered is *disable with a reason* and *enable*. Four stat cells count operators across the whole table rather than the page being looked at. Filters: search (username or display name), role, and active / disabled / both. Each row prints the role badge, the permissions count with the full list on hover, and — for a row seeded before the role vocabulary existed — the raw stored value beside the normalised one, because a screen that shows only `SUPER_ADMIN` hides a row that still needs migrating. A card under the table lists all four roles with every permission they carry, read from `GET /api/admin/operators/roles`, which is the table the guards themselves use; `operator:manage` is highlighted because it is the only permission that reaches this screen and it sits on `SUPER_ADMIN` alone. The three refusals the server would answer with are said **before** the click: your own row's Disable button is disabled with "another super-admin has to do it", and when the roster holds exactly one active super-admin, disabling *or demoting* it is blocked with the lockout explained — the count comes from a separate query because the guard asks about the table, not the page. Creating takes a lowercase username, an 8-character minimum password and a role, and the form shows what that role can do before it is saved; editing changes role and display name only, since **there is no password route in this router** — an administrative reset without the operator's own credential is a way to take an account without leaving a reason. The disable dialog needs a reason of at least 8 characters (its button stays dead until there is one) and states what the switch actually does: sign-in refused, and a token already issued refused on the *next* request, because every admin call re-reads the row. A disabled account keeps its password hash, its name in the audit log and its history. Everything here needs `operator:manage`, so `FINANCE_ADMIN` and below get `403 permission_denied` on every route in the family |
| `/agencies`     | The agency book (`agencies`, `agency_hosts`, `agency_settlements` — migration `0033`): what the platform owes each roster of hosts, and the batches that clear it. Two rules shape the screen and neither is taste. **It never moves money** — the accrual is written by the gift path, so the only button that reaches the journal is Pay, and Pay records a transfer that already happened on someone else's rails, which is why it takes a reference instead of an amount. **It never shows a rate without the level it came from** — a host is taken at their own override, their agency's rate, or the platform default, and `commissionLabel` says which in words because the number alone cannot answer the question an agency asks. Tabs: *Agencies & rates* (whole-table count) and *Settlement batches* (open batches, red when non-zero). The roster prints, per agency, the rate a new host inherits with `set here: X%` beside it, active/total hosts, commission counted in R-coins ("the same money, in the unit an agency negotiates in"), what is owed now with `claimed` and `held` under it, open/paid batch counts, and `no account yet` with the reason on hover when no gift has reached its hosts. The desk behind each row gives the four position cells (Available / Claimed by open batches / Held by a dispute / Balance) read from the account's own `balanceSource`, its lifetime in and out against the balance it claims, the agency rate, the roster with a `HOST`/`AGENCY`/`PLATFORM` badge per host, and that agency's batches; saving the agency rate re-reads the desk rather than patching one field, because the server — not the panel — is what labels every inheriting host. A rate input is never blank-as-unchanged: empty means *clear the override* and is sent as `null`, since the server refuses a write that omits the field instead of guessing which of the three levels the operator meant. The **Platform default rate** card edits `accounts.agency.defaultCommissionBps` and recomputes a worked example while typing ("A 100 R-coin gift would accrue PKR 0.90 at this rate"), prints `unset — treated as 0` for a null so an invisible zero is visible, and says on save that the dial applies to the next gift, not to accruals already booked. Batches go DRAFT → APPROVED → PAID with VOID from either open step, and the action column changes verb with the row: Approve only on DRAFT, *Record payout* only on APPROVED, Void never on a paid row — which prints its `payoutReference` and method under the badge, an approved row prints **who** approved it, and a draft prints "awaiting a second operator". The period is half-open and says so under the dates (`the end day is not included`); `What it paid` opens the accruals behind the batch with the sum identity printed above them, so a disputed figure is answered with the gift list rather than re-derived. Raise takes an agency, two days and an optional method with a per-click idempotency key — a retry after a lost response returns the batch that already exists and the toast says "this is its first answer, not a second batch" — and the modal states before submitting what the agency is owed and how much of it open batches already claim, because `nothing_to_settle` and `settlement_exceeds_payable` are both refusals the numbers on screen predict. Approve shows the amount and says approval changes no balance; the server's `403 self_approval` is shown in the same modal, which is the only place an operator learns that the person who raised a batch cannot sign it. Void needs a reason of at least 8 characters, reports how many accruals go back to the unsettled pool and that the hold is released, and says a paid batch takes a correcting entry rather than an edit. Reading needs `finance:read` (which is also what puts the link in the sidebar), every write needs `commission:manage`, and the platform dial needs `config:manage` — so a `FINANCE_ADMIN` can settle a batch and read the dial but cannot move it. |
